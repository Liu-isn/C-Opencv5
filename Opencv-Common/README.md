# Common 模块目录说明 README.md

## 1. 模块简介

Common 是整个解决方案的 通用基础公共库，为所有业务模块提供与业务无关的底层通用能力。

职责边界：

- 只存放 通用、基础、工具类 代码：日志、文件操作、字符串处理、基础数学、通用工具、系统辅助接口

- 不存放任何业务代码（图像、算法、业务逻辑、模块专属DLL导出宏等）

- 所有业务模块（TestImage、主程序、其他业务DLL）均可依赖 Common，Common 禁止反向依赖业务模块

编译形态：支持编译为 Static Lib / Dynamic DLL（根据项目配置决定）。

## 2. 整体目录结构

Common 工程完整目录结构如下（标准可拓展架构）：

```Plain Text
Common/
├─ include/                 # 对外公开头文件（外部项目唯一可引用目录）
│  └─ common/               # 命名空间隔离，防止头文件重名
│
├─ src/                     # 模块内部实现源码 & 私有头文件
│  ├─ log/                  # 日志模块
│  ├─ file/                 # 文件读写、路径工具
│  ├─ string/               # 字符串通用处理
│  └─ math/                 # 基础数学计算工具
│
├─ private_include/         # 内部全局私有头文件（仅Common内部使用，不对外暴露）
├─ props/                   # VS 统一属性表（编译配置、宏、字符集、警告等级）
├─ tests/                   # Common 单元测试代码（GTest）
└─ thirdparty/              # Common 依赖的轻量级第三方库（局部私有依赖）

```

## 3. 各目录详细职责

### 3.1 include/ 【对外公共接口】

所有 允许外部项目引用 的头文件全部放在这里。

规范：

- 外层工程仅需配置 `Common/include` 即可使用全部公共能力

- 统一引用格式：`#include <common/xxx.h>`

- 若 Common 自身为 DLL，此处放置`common_api.h` 导出宏

禁止放入：模块内部实现头文件、业务相关代码、其他模块（TestImage）的导出宏。

### 3.2 src/ 【内部实现】

按功能垂直拆分子目录，所有 cpp、内部私有 .h 放在此处。

拆分原则：

- log/：日志封装、日志输出控制

- file/：文件读取、写入、路径判断、文件夹遍历

- string/：字符串裁剪、编码转换、格式化工具

- math/：基础数学计算、数值限制、坐标通用计算

该目录 不对外暴露，外部工程禁止引用 src 内任何文件。

### 3.3 private_include/ 【内部公共私有头】

存放多个 src 子模块共用、但不需要对外暴露的私有定义、结构体、内部宏。

仅 Common 工程内部可包含。

### 3.4 props/ 【编译统一配置】

存放 VS 属性表 `.props`，统一控制：

- C++ 标准、字符集、编译警告等级

- 全局预处理器宏

- 统一包含目录、库目录规则

### 3.5 tests/ 【单元测试】

存放 Common 所有工具类、函数的单元测试用例。

独立测试工程，不参与正式业务编译。

### 3.6 thirdparty/ 【局部第三方依赖】

仅存放 Common 专属的轻量级第三方依赖（如日志库、工具类头文件库）。

全局大型第三方库（OpenCV 等）统一放在解决方案根目录 thirdparty，不放在 Common。

## 4. 重要规范约束

### 4.1 代码分层约束

- ✅ Common：纯基础、无业务、无模块耦合

- ✅ 业务模块（TestImage 等）依赖 Common

- ❌ Common 禁止依赖任何业务模块

- ❌ TestImage 模块的 `XXX_API` 导出宏严禁放入 Common

### 4.2 头文件暴露规范

- 对外功能：`include/common/`

- 内部实现：`src/`、`private_include/`

## 5. DLL 导出宏规范区分

- Common 自身导出宏：`common_api.h`（本模块内部）

- TestImage 业务模块导出宏：归 TestImage 工程所有，与 Common 完全隔离

## 6. 拓展原则

后续新增通用能力，按照如下规则新增：

1. 新功能新建 src 子文件夹

2. 对外接口放入 `include/common/`

3. 内部实现放入 src 对应模块

4. 配套单元测试放入 tests/
